# 显示延迟：已修复内容与待研究问题

> 2026-11-17 后续研究及 W 最终验收交接见 [Original 延迟研究交接](research/original-render-latency/README.md)。本文保留 0.1.4 的发布背景；下方“下一步研究”是当时计划，不代表最新状态。W 尚未集成，最终验收未完成。

更新：2026-11-16。对应版本：0.1.4 / build 5。

## 本版修了什么

Original 实时串流新增最多两帧的「等待实际显示」限制。原有 GPU 信号量只管 GPU 是否完成，不能阻止已经渲染完的画面继续在显示管线里堆积。新增限制在取下一帧前生效，实际显示回调才归还名额；取消未提交的绘制、GPU 错误和重复回调都有对应处理。

保留 MTKView 调度、原有着色器、两帧输入队列及原有过期/追帧策略。MetalFX 和 Integer 不启用这项限制，但其待显示提交仍计数，切回 Original 时不会忽略它们。没有接入实验中的 AVSampleBufferDisplayLayer、工作线程渲染或固定相位定时器。

本版也扩充了导出诊断的逐帧事件：提交、GPU 开始/完成、实际显示，以及输入覆盖、过期、追帧、渲染器替换和未显示。报告 schema 为 10；`scripts/analyze-presentation-trace.py` 可分析 schema 9/10，旧报告没有的阶段不会被当成零。

## 已验证的收益及边界

M1 Mac mini，LG 4K 60 Hz 显示器，Standard/Balanced、1080p60 云端游戏标题画面、Original、原生全屏、Detailed HUD。最终两轮各十二段，每段 12 秒，六段旧路径、六段新路径；顺序 A B B A B A A B A B B A。分析去掉每段前 3 秒和后 1 秒，采样期间不编译、不运行 profiler。

| 实验 | 旧路径 | 新路径 | 能说明什么 |
| --- | --- | --- | --- |
| 每段主动增加一次绘制的压力测试 | 最多三帧待显示；两段 Display wait 中位数持续在 39.55 / 47.20 ms | 最多两帧；六段均为 22.34–22.60 ms | 可以防止该触发条件下额外堆积 |
| 无额外绘制的普通串流 | Display wait 中位数 22.4–22.7 ms | 同为 22.4–22.7 ms，六段均未触发限流 | 正常状态基本持平，不能宣称普遍快了一帧 |

两边稳定输出都接近 60 fps。普通串流中大于 25 ms 的显示间隔旧/新分别为 5/4 个，大于 40 ms 为 0/1 个；短样本不足以证明长期游戏顺滑度。压力测试是验证机制，不能把它的改善直接当成日常平均收益。

正式代码通过 213 项测试，包括名额释放和并发重复回调。两次真实会话检查了首帧、全屏进出、MetalFX 切回 Original、结束及重新连接，没有卡死或解码错误。模式切回后 HUD 曾显示 59.5 fps、Display wait 均值 22.5 ms / p95 23.2 ms、arrival → display 均值 34.0 ms / p95 45.6 ms。这些是滚动 HUD 快照，不是额外的 A/B 结论。全屏切换期间仍会丢帧。

## 数字的含义

- `arrival` 是解码帧交付给 XFrame 的时刻，不是网络包到达；`arrival → display` 不包含网络传输及此前的解码耗时。
- `display` 使用 drawable 的实际 `presentedTime`，不是计划显示时间。一次独立 Metal System Trace 中，它与对应系统 display-surface swap 时间的差异小于 0.009 ms；这仍不是测量屏幕发光或输入到光子的延迟。
- 各阶段 p95 来自不同帧，不能相加得到总延迟 p95。
- `Skipped total` 是会话累计值。要看固定区间增量、原因和实际显示间隔，不能仅凭总数上涨断言算法退化。
- 导出仅包含有界事件尾部。缺少起点/终点的帧不能用于完整时序；分析脚本的待显示计数只覆盖成功关联的视频帧，不包含所有重复绘制。

## 下一步研究

### 1. 正常约 23 ms 的 GPU → display 等待从哪里来

这是最重要的未解问题。Original GPU 本身约 0.5–0.6 ms，正常显示等待仍跨越一个以上 60 Hz 周期。尚不能认定是 macOS 固定下限、WindowServer bug 或 MetalFX 导致。

下一轮同时记录：显示回调的目标刷新时间、CPU 提交、GPU 完成、WindowServer 读取视频表面及最终 swap。比较同一刷新相位的最简 Metal 窗口和 XFrame，查明哪一轮合成真正接纳画面。分别控制 HUD、窗口层级与全屏形式，避免一次改变多个变量。不要把减少帧前等待、却增加帧后等待算作收益。

验收：至少五组同场景配对，实际 arrival → display 的中位数及尾延迟下降，实际显示间隔不退化，重复运行仍成立。

### 2. 较晚提交能否既减少等待又不漏掉刷新

主线程延后提交曾减少约 4 ms，但偶发晚到会额外增加一个刷新周期。加入 deadline 检查后能控制部分风险，却增加短帧间隔缺口；固定毫秒参数还依赖机器和刷新率。

应先区分主线程阻塞、定时唤醒迟到和 drawable 获取耗时，再考虑按实际显示期限调度。此前工作线程实验的主要失败是唤醒迟到，不能由此断言所有工作线程方案无效。不能直接发布针对 M1/60 Hz 调好的固定偏移量。

### 3. 输入等待与丢帧策略是否还能改进

输入队列与待显示队列是两层不同的队列。现有输入最多两帧，超过 50 ms 过期，队首超过 25 ms 且后帧就绪时追帧。它们本次没有变化。

用 schema 10 按帧关联过期、追帧、覆盖、未显示及最终帧年龄，分别看稳态、网络抖动和界面切换。总是取最新帧的实验以约 2 fps 的损失换来约 2 ms，未采用。后续不以隐藏计数、扩大缓冲或更多丢帧来制造好看的延迟数字。

### 4. M5、不同屏幕和长期真实游戏

用户的 M5 内屏及外接屏曾出现不同显示等待；这些不是控制条件完全相同的 A/B。0.1.4 需要先验证 M5 的 Original 是否还出现持续额外排队，再决定是否扩展策略。

建议对照同一游戏场景、同一画质/帧节奏设置，分别记录内屏和外屏的实际刷新率、Original/MetalFX、窗口/全屏、HUD 模式。旧版与新版各观察至少 60 秒，记录运行时长和 Skipped 增量，并导出诊断；若发生持续高延迟，在状态仍存在时导出。不要同时更新网络、分辨率和渲染设置。再做较长游戏会话和多次切换/重连，覆盖短标题画面测试未验证的情况。

### 5. MetalFX 单独研究

工作线程路径在五组 MetalFX 对照里曾降低延迟，但 Original 没有得到相同收益。两者不可混用结论。本版不改 MetalFX 调度；后续需针对 GPU 成本、提交相位、显示队列和实际画面质量独立验收。

## 已试过但不能直接采用的办法

| 方案 | 结果 / 拒绝原因 |
| --- | --- |
| 只允许一帧等待实际显示 | 输出降到约 30 fps，正常显示等待仍未消失 |
| 仅把 drawable 数量设为二 | 不等同于限制实际待显示帧数，未解决问题 |
| Moonlight 风格 AVSampleBufferDisplayLayer | 部分场景帧年龄降低，但实际显示节奏退化；内部零丢帧计数不代表每帧都上屏 |
| Original 工作线程渲染 | 多组对照无一致收益，有时只是转移等待 |
| 关闭显示同步 | 改变了显示行为和测量边界，未证明无撕裂且同等顺滑 |

后续如重试，应说明新假设及与旧实验的区别。性能验收始终使用实际显示结果；计划时间、平均 FPS、编译成功都不能替代它。
