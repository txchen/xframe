# VideoToolbox 720p / 1080p interpolation gap: primary-source review

2026-09-23. Scope: `VTLowLatencyFrameInterpolationConfiguration` + `VTFrameProcessor` on the current Apple M1 / macOS 27.0 machine. This note combines repeated measurements, local process sampling, and Apple API contracts. It does not infer undocumented internals from the API name.

## Reproduction and explanation supported by measurements

The reproducible command is `scripts/benchmark-frame-generation/recheck-vt-resolutions.sh`. It compiles the existing standalone VideoToolbox benchmark, transcodes the bundled 1080p30 fixture to a native 720p30 clip, and runs 60 adjacent-frame interpolations per trial in the alternating order 720, 1080, 1080, 720, 720, 1080. Each trial discards the first five interpolation times. The generated clips and full per-frame timing data stay under `.build/`; [the M1 run summary](vt-resolution-repeat-m1.json) retains fixture hashes, macOS/device, decode time, and process CPU time.

| M1/macOS 27 run | 720p median / p95 | 1080p median / p95 |
| --- | ---: | ---: |
| First paired runs | 5.47 / 5.92 ms | 89.30 / 90.23 ms |
| Second paired runs | 5.46 / 5.94 ms | 86.16 / 90.65 ms |
| Third paired runs | 5.45 / 5.95 ms | 86.49 / 90.27 ms |

The 720p result is 15–16× faster despite having only 2.25× fewer pixels. Decode medians are 0.05–0.06 ms at 720p and 0.10–0.12 ms at 1080p, outside the measured `process` interval. `/usr/bin/time -lp` reports only **0.04–0.05 s of process user CPU time** for a complete 720p trial, but **4.14–4.19 s** for a 1080p trial. The result does not depend on test order or on a single slow startup call. The earlier in-app measurement agrees with both ranges.

To control for the in-app benchmark's different buffer provenance and video content, the checked-in [synthetic VideoToolbox probe](../../scripts/probe-vt-interpolation.swift) was also run at both sizes. It creates input and output surfaces from each configuration's own attributes and repeatedly processes an identical pair. After warmup, 720p was about 5.3 ms and 1080p about 86–89 ms. The gap therefore persists without codec decode, fixture resize, moving video content, or different buffer construction methods.

The configurations also report the same source/destination pixel format (`875704438`, NV12 video range), IOSurface requirement, and zero extended pixels; only width and height differ. That makes a caller-selected pixel format or explicit quality flag an unlikely cause of this comparison.

`/usr/bin/sample` observed the VideoToolbox `VideoInterpolationQueue` in the Apple Espresso ML runtime in both synthetic-size trials. In the 720p sample, **921 of 955** sampled queue stacks were in the AppleNeuralEngine request path, with no `Espresso::resample_kernel_cpu::__launch` stacks. In the 1080p sample, **729 of 1,409** sampled queue stacks were in `Espresso::resample_kernel_cpu::__launch`, about **299** in CPU/ANE context transfer, and **279** in the AppleNeuralEngine request path. A separate 1080p real-video sample showed the same CPU-resample and transfer functions. These are stack-sampling counts, not exact per-frame stage durations or ANE hardware utilization. They establish a concrete difference: **1080p invokes substantial host CPU resampling and host/ANE transfer inside Apple's processing stack; 720p predominantly waits for ANE processing.** This accounts for much of the wall-time gap and the 100× difference in process CPU seconds. It does **not** show a complete fallback from ANE to CPU: 1080p still makes ANE requests.

The causal reason Apple chooses that internal path remains unpublished. One plausible explanation is that the 1080p workload crosses an internal model/shape boundary and needs host-side resampling, but the sample cannot establish the model's native dimensions or the exact selection rule. Repeated measurements and stack symbols support the CPU-work explanation; any claim of a specific model switch, tiling scheme, or GPU-versus-ANE threshold would go beyond the evidence.

## What Apple actually specifies

1. Apple calls the `VTFrameProcessor` effects **ML-based video-processing algorithms optimized for Apple silicon**. It describes the low-latency interpolation effect as intended for real-time video conferencing and live streaming, but publishes no per-resolution time guarantee in the [WWDC25 presentation](https://developer.apple.com/videos/play/wwdc2025/300/). “Low latency” is a use-case/design description, not a promise that 1080p finishes within a 30 fps frame interval on every supported Mac.
2. The [low-latency interpolation configuration](https://developer.apple.com/documentation/videotoolbox/vtlowlatencyframeinterpolationconfiguration) accepts source width, height, and a requested number of interpolated frames. Apple warns that **ML model loading** during `startSession` can exceed one frame interval. The installed macOS SDK makes the same statement in `VTFrameProcessor_LowLatencyFrameInterpolation.h:26-59`. Thus a model is involved, but neither source identifies its architecture or its compute device.
3. The low-latency configuration's public interface has **no quality/performance priority, model revision, compute-unit, or algorithm selector** (`VTFrameProcessor_LowLatencyFrameInterpolation.h:44-123`). A *different* API, `VTFrameRateConversionConfiguration`, does expose `qualityPrioritization`, optical-flow and revision choices (`VTFrameProcessor_FrameRateConversion.h:22-35,77-91`). Its documented knobs must not be attributed to the low-latency API. Both headers are from the Apple macOS SDK at `/Library/Developer/CommandLineTools/SDKs/MacOSX.sdk/System/Library/Frameworks/VideoToolbox.framework/Headers/`.
4. Apple defines separate [maximum dimension](https://developer.apple.com/documentation/videotoolbox/vtlowlatencyframeinterpolationconfiguration/maximumdimension%28forspatialscalefactor%3A%29) and [maximum total pixel count](https://developer.apple.com/documentation/videotoolbox/vtlowlatencyframeinterpolationconfiguration/maximumpixelcount%28forspatialscalefactor%3A%29) checks. Pass spatial factor `1` for temporal-only interpolation (`VTFrameProcessor_LowLatencyFrameInterpolation.h:102-121`). The XFrame M1 export reports a 2,073,600-pixel maximum: 1920×1080 sits **exactly at that limit**, while 1280×720 is 921,600 pixels (44.4% of the limit). This proves both sizes occupy different positions within the supported range; it does **not** prove that the implementation changes model, tiling, compute engine, or quality at either size. Apple DTS also advises checking support and measuring performance on target hardware because availability does not guarantee useful performance; its [forum answer](https://developer.apple.com/forums/thread/821701) addresses device support rather than this specific M1/1080p gap.
5. `VTFrameProcessor` offers asynchronous completion and a separate API for inserting work into an application's [Metal command buffer](https://developer.apple.com/documentation/videotoolbox/vtframeprocessor). Its Apple SDK declaration says the asynchronous completion handler is called when frame processing completes (`VTFrameProcessor.h:74-105`). XFrame times the async `process(parameters:)` sequence from submission through one returned output, so the report is correctly labeled **processor wall time**, not GPU execution time. In a caller-owned Metal command buffer, Apple documents [GPU start/end timestamps](https://developer.apple.com/documentation/metal/mtlcommandbuffer/gpuendtime) for measuring that buffer's GPU interval, but this does not expose per-kernel timing or other internal work in the present async call.

## What these sources cannot explain

No reviewed Apple documentation states a 720p/1080p threshold, a resolution-dependent model selection rule, an ANE↔GPU fallback, a codec-engine path, a tile count, or a fixed per-resolution cost for **this** effect. Apple’s broader description as ML-based does not imply that the VideoToolbox hardware encoder/decoder runs interpolation. The local samples show that both sizes invoke ANE APIs, with substantial CPU resampling and transfers observed at 1080p; they do not disclose why the framework makes those choices.

The in-app benchmark has an input-provenance difference: at 1080p it feeds decoded fixture pixel buffers directly; at 720p it first creates new IOSurface-backed buffers and copies/resizes through `VTPixelTransferSession` (`Sources/XFrame/PostProcessingBenchmark.swift:310-357`). Resizing is excluded from both timed intervals, but buffer layout, stride, cache state, attachments, or copy history might still affect the result. The equal-provenance synthetic probe reproduces the gap, so this difference is **not necessary** to produce it. An exact layout/stride comparison remains open.

## Remaining questions

- A small synthetic size sweep ran successfully at 640×360, 960×540, 1152×648, 1280×720 and 1920×1080. Several intermediate requests, including 1440×810 and 1600×900, created configurations but failed at `process` with `com.apple.VideoProcessing -12911` (processor not initialized). This makes a simple continuous size/performance curve misleading. A controlled sweep with recorded buffer attributes could locate a valid-size boundary, but it would not identify Apple's unpublished selection rule.
- Compare the async API with caller-owned `processWithCommandBuffer` plus Metal command-buffer GPU timestamps, if it succeeds for this configuration. Correlate with GPU/Neural Engine activity using Apple's [Core AI/Instruments profiling guidance](https://developer.apple.com/documentation/CoreAI/analyzing-model-runtime-performance-with-instruments), while recognizing that private VideoToolbox model events may not appear as caller-owned Core AI events. On this machine only Command Line Tools are installed; `xcrun -f instruments` fails, so an Instruments trace requires a full Xcode installation.
- Inspect the generated frame for both sizes. A fast path that silently drops quality or returns a near-copy would be a very different result from a genuinely efficient interpolator. Latency and temporal artifacts need live-stream validation after throughput is understood.

The current practical conclusion is: **on this M1/macOS 27.0, 1080p low-latency interpolation is over the 33.33 ms 30→60 budget because Apple's processing stack performs substantial CPU resampling and host/ANE transfers in addition to ANE execution. Apple does not publish why this path appears at 1080p.** The 720p time excludes any downscale/upscale needed for a higher-resolution stream; the M5 must be measured separately.
