# Moonlight macOS latency and presentation research

Date: 2026-09-22. Research only; no application code changed or downloaded code executed.

Follow-up: [local presentation latency issue and controlled A/B plan](issues/02-local-presentation-latency.md).

## Result

There is no verified official M1 Mac mini benchmark here that establishes a universal Moonlight receive-buffer + decode + actual-on-screen delay of 5 ms, 10 ms, or any other small number. Official documentation explicitly warns that metrics can differ across clients and omit system/display latency. The current XFrame approximately 40 ms client-side subtotal should be investigated, but comparing it directly to Moonlight's small rendering number would be misleading. [Official metrics documentation](https://github.com/moonlight-stream/moonlight-docs/wiki/Frequently-Asked-Questions#what-do-the-numbers-mean-in-the-on-screen-connection-statistics)

Official FAQ guidance: frame queue delay should generally be shorter than one frame period; V-Sync can add a refresh period to rendering. At 60 Hz a period is approximately 16.7 ms. These are distinct stages, not an official total-latency benchmark, and current backend implementations need inspection rather than trusting the generic label. [Official latency definitions](https://github.com/moonlight-stream/moonlight-docs/wiki/Frequently-Asked-Questions#latency-numbers)

## Released v6.1.0 macOS path

- Hardware VideoToolbox decoding prefers the Metal renderer. AVSampleBufferDisplayLayer is a fallback when Metal cannot be used; it is not the default hardware path in this version. [Renderer selection](https://github.com/moonlight-stream/moonlight-qt/blob/f786e94c7b2f943e24e65d7d74deb539b827fc84/app/streaming/video/ffmpeg.cpp#L887-L943)
- The render thread waits for renderer readiness **before dequeuing the frame**. Metal's `waitToRender()` obtains the next drawable, then throttles when more than two presentations are pending. This avoids choosing an already old frame before a drawable wait. [Pacer render thread](https://github.com/moonlight-stream/moonlight-qt/blob/f786e94c7b2f943e24e65d7d74deb539b827fc84/app/streaming/video/ffmpeg-renderers/pacer/pacer.cpp#L128-L171), [Metal readiness](https://github.com/moonlight-stream/moonlight-qt/blob/f786e94c7b2f943e24e65d7d74deb539b827fc84/app/streaming/video/ffmpeg-renderers/vt_metal.mm#L213-L234)
- Three drawables are deliberate. The source comment says two drawables can force a composited path, especially windowed, making latency worse; three enables an offloaded direct path. This is a historical backend rationale, not a guarantee about every macOS version. Blindly reducing XFrame's drawable count to two is not an evidence-backed fix. [Drawable count rationale](https://github.com/moonlight-stream/moonlight-qt/blob/f786e94c7b2f943e24e65d7d74deb539b827fc84/app/streaming/video/ffmpeg-renderers/vt_metal.mm#L740-L751)
- Rendering submits the drawable and waits for the **GPU command buffer** to complete. An independent `addPresentedHandler` decrements the pending-presentation count; the render call does not wait for this callback. Thus the renderer function duration is not actual onscreen presentation latency. [GPU completion and presentation callback](https://github.com/moonlight-stream/moonlight-qt/blob/f786e94c7b2f943e24e65d7d74deb539b827fc84/app/streaming/video/ffmpeg-renderers/vt_metal.mm#L630-L654)
- Pacer statistics measure decoded-frame timestamp → renderer entry as queue time, and renderer entry → return as render time. Consequently, even adding queue + render in this backend omits the later drawable-to-display completion delay. [Exact timer boundaries](https://github.com/moonlight-stream/moonlight-qt/blob/f786e94c7b2f943e24e65d7d74deb539b827fc84/app/streaming/video/ffmpeg-renderers/pacer/pacer.cpp#L333-L349)

## Current master: useful optimization reference, not a released baseline

- With Apple Silicon, macOS 14+, and V-Sync enabled, the Metal renderer starts `CAMetalDisplayLink`, requests `preferredFrameLatency = 1`, and requests the stream's frame rate. It uses the main run loop's common modes, so it is not entirely independent of UI scheduling. [Display-link setup](https://github.com/moonlight-stream/moonlight-qt/blob/032529d782242e3833e0b3b147dbbf96e878e3ca/app/streaming/video/ffmpeg-renderers/vt_metal.mm#L809-L824)
- The renderer transfers a decoded frame into a single latest-frame slot, replacing any older frame not yet rendered. The display-link callback obtains its supplied drawable, may wait up to half the remaining deadline for a fresh frame, then renders. This minimizes stale-frame backlog; it does not guarantee zero skips. [Latest-frame handoff](https://github.com/moonlight-stream/moonlight-qt/blob/032529d782242e3833e0b3b147dbbf96e878e3ca/app/streaming/video/ffmpeg-renderers/vt_metal.mm#L599-L625), [deadline-aware callback](https://github.com/moonlight-stream/moonlight-qt/blob/032529d782242e3833e0b3b147dbbf96e878e3ca/app/streaming/video/ffmpeg-renderers/vt_metal.mm#L907-L980)
- In that asynchronous display-link branch, `renderFrame()` ends after publishing into the slot. Pacer render-time statistics therefore do not include subsequent display-link waiting **or even the later GPU rendering**. They cannot be compared to XFrame's decode-complete → actual drawable presentation measurement. [Pacer timing](https://github.com/moonlight-stream/moonlight-qt/blob/032529d782242e3833e0b3b147dbbf96e878e3ca/app/streaming/video/ffmpeg-renderers/pacer/pacer.cpp#L333-L346), [async handoff](https://github.com/moonlight-stream/moonlight-qt/blob/032529d782242e3833e0b3b147dbbf96e878e3ca/app/streaming/video/ffmpeg-renderers/vt_metal.mm#L595-L615)
- The generic Pacer bounds queues and drops backlog adaptively based on 500 ms history; the maximum of three is a bound, not a policy to always accumulate three frames. On macOS this generic pacing layer has no Windows/Wayland V-Sync source, so Metal's own path matters. [Queue bound](https://github.com/moonlight-stream/moonlight-qt/blob/032529d782242e3833e0b3b147dbbf96e878e3ca/app/streaming/video/ffmpeg-renderers/pacer/pacer.cpp#L16-L25), [V-Sync platform selection](https://github.com/moonlight-stream/moonlight-qt/blob/032529d782242e3833e0b3b147dbbf96e878e3ca/app/streaming/video/ffmpeg-renderers/pacer/pacer.cpp#L283-L303), [adaptive backlog control](https://github.com/moonlight-stream/moonlight-qt/blob/032529d782242e3833e0b3b147dbbf96e878e3ca/app/streaming/video/ffmpeg-renderers/pacer/pacer.cpp#L351-L391)
- Current master can instead prefer libplacebo/MoltenVK when compiled with that support and configured AUTO/VULKAN. Explicit AVSBDL selects AVSampleBufferDisplayLayer; otherwise selection reaches Metal. Do not claim all current Moonlight macOS installations use one identical backend. [Current selection](https://github.com/moonlight-stream/moonlight-qt/blob/032529d782242e3833e0b3b147dbbf96e878e3ca/app/streaming/video/ffmpeg.cpp#L1008-L1023)
- AVSBDL's render call ends after `enqueueSampleBuffer`, likewise without an actual displayed timestamp. [AVSBDL submission](https://github.com/moonlight-stream/moonlight-qt/blob/032529d782242e3833e0b3b147dbbf96e878e3ca/app/streaming/video/ffmpeg-renderers/vt_avsamplelayer.mm#L280-L304)

## XFrame comparison and next experiment

Verified local XFrame source: `Sources/XFrame/LocalVideo.swift:10` timestamps `VideoFrame.arrivedAt`; `Sources/XFrame/MetalRenderer.swift:154-158` measures queue-to-submit separately and decode-callback arrival → `drawable.presentedTime` for presentation. The latter includes queue, GPU and OS presentation waiting. It must not be added to the queue/GPU durations again. Three in-flight permits are released at GPU completion, not actual presentation. These are local source observations, not measured Moonlight results.

The live HUD network + client estimate implies a local subtotal around 40 ms in this session. The receiver jitter buffer was approximately 1 ms; separately recorded tail statistics were decode p95 approximately 3 ms, GPU p95 approximately 0.5 ms, frame-wait p95 approximately 16.5 ms, and post-decode presentation p95 approximately 40.2 ms. These percentiles cannot be added/subtracted to reconstruct the mean subtotal. Thus describing all 40 ms as generic receive buffering obscures the dominant stage. The useful target is post-decode scheduling/presentation, not codec replacement or a larger FIFO.

Suggested controlled experiment (inference, not a proven fix): compare the current timer-driven MTKView with a display-link deadline-driven renderer, preserve presented-time instrumentation, and measure draw-start→submission→GPU completion→actual presentation independently. Test fresh-frame selection and presentation-depth bounds while preserving output cadence. Hold controller input, resolution, V-Sync, window mode, and HUD mode constant; record skip **rate**, not just cumulative total. Do not lower the displayed metric by stopping the clock at GPU completion, and do not declare lower latency from a Moonlight-style timer alone.

A small number of deliberate stale-frame skips can be the cost of bounded latency; “never skip” is not by itself a correct objective for an interactive stream. The official FAQ identifies late/early frames and jitter as causes of pacing skips. [Frame-drop definitions](https://github.com/moonlight-stream/moonlight-docs/wiki/Frequently-Asked-Questions#frame-drop-numbers)

Apple defines `presentedTime` as when the drawable was displayed onscreen, and warns `preferredFrameLatency` is a request whose final latency may be larger, especially windowed on macOS. A one-frame request is not a guaranteed end-to-end limit. [Presented time](https://developer.apple.com/documentation/metal/mtldrawable/presentedtime), [preferred frame latency](https://developer.apple.com/documentation/quartzcore/cametaldisplaylink/preferredframelatency).
