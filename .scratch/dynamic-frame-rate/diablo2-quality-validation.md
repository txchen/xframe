# Diablo II: Resurrected quality-mode timing test — 2026-09-22

The user switched Diablo II: Resurrected to its in-game quality mode and played for about a minute. I exported schema-9 stream diagnostics from the active XFrame Cloud Games window to `.build/fixtures/diablo2-quality.json`, preserved the [full report](samples/diablo2-quality-01.json), and derived a [30-second timing sample](samples/diablo2-quality-30s.json) from report seconds [80, 110). The clipped sample contains numeric frame events only; no gameplay image or audio is retained. Full-report SHA-256: `ea7113356c0a24f1c84ba899bad0be39af9f6c416d6a082f5380a037c3b3c0f2`.

The HUD during export showed native decoded video **2560×1440**, HQ session profile requested, STREAM and OUT approximately 30 fps, zero decoder errors, and zero reported RTP packet loss/NACKs. The user confirmed the in-game quality mode. The report's first 37 seconds include roughly 60 fps and transitions; from report second 38 through at least 110, decoder input, decode, and display remain around 30 fps. This confirms a sustained **encoded-frame cadence** near 30 fps in this session. It does not prove every encoded frame has unique game content; moving-image quality still requires image samples.

The clipped 30-second interval has 899 decoder-input access units over 29.96 seconds (**29.97 fps**); decoded and delivered counts are 900 because the cut intersects an in-flight frame, and there are 897 presentation events. Median RTP interval is 33 ms, p95 34 ms, maximum 37 ms. Median local decoder-input interval is 33.48 ms, p95 41.08 ms, with two notable delivery stalls including a 123 ms maximum. Matched decoder-input-to-completion time is median 4.29 ms and p95 4.9 ms. Matched delivery-to-presentation time is median 32.54 ms and p95 39.97 ms. Counters from the full session include the earlier mode transition, so they are not used as a stable-clip loss rate.

The [60 Hz replay](samples/diablo2-quality-30s-evaluation.json) assigns 899 original frames and 899 generated midpoints to 1,798 output ticks, with no missing decoded references and no source-frame tick collisions. Modeled reference-ready delay is median 13.43 ms, p95 29.42 ms, p99 37.36 ms. Two upstream delivery stalls produce isolated modeled requirements up to 121.71 ms. A live implementation should miss/fallback on such stalls rather than buffer every frame that long. This delay model is anchored to the first decoder input and excludes actual interpolation processing and display scheduling; it is **not measured incremental input-to-display latency**.

A read-only capability query on this Apple M1 / macOS 27 host found `VTLowLatencyFrameInterpolationConfiguration.isSupported == true`, but `maximumPixelCount(forSpatialScaleFactor: 1) == 2,073,600` and `maximumDimension(forSpatialScaleFactor: 1) == 1,920`. The current 2560×1440 stream has 3,686,400 pixels, above that advertised limit. Constructing a configuration object returned non-nil; that is not evidence that a processing session can handle this size. Before selecting Apple's low-latency backend, test a real session at supported size or assess another native-size backend. Changing xCloud's requested stream quality to 1080p while keeping Diablo II's in-game quality mode is a possible test, but its visual tradeoff needs user acceptance. The M5 MacBook Air must be queried separately.

This capture validates the **30→60 scheduling target** and supplies a replayable timing workload. It does not validate frame quality, 1440p backend support, real-time GPU throughput, or controller feel. No interpolation was enabled during this test.
