## Two separate quality controls

1. **HQ resolution/profile preset:** Display settings expose `720`, `1080`, and `1081`, with the last labeled `1080P(HQ)/1440P`. Session creation maps these to client OS names `android`, `windows`, and `tizen`. The value is sent both in JSON `settings.osName` and in `X-MS-Device-Info` → `dev.os.name`; this is a client capability/profile request, not an explicit Xbox Series X/S host selector. The device header also declares a 4096×2160 display. The same session-start implementation serves cloud and home streams. Sources: [display.ts L5-L16](https://github.com/Geocld/XStreaming/blob/383e19d324f2d3029d1c304752f4d38a9360bb95/src/common/settings/display.ts#L5-L16), [xCloud/index.ts L323-L414](https://github.com/Geocld/XStreaming/blob/383e19d324f2d3029d1c304752f4d38a9360bb95/src/xCloud/index.ts#L323-L414).

   Upstream help text says HQ supports bitrate >=15 Mbps and that 1440p is available only for some cloud titles, not home streaming. This is the project's claim; actual entitlement, resolution, and throughput require live verification. [en.ts L94-L98](https://github.com/Geocld/XStreaming/blob/383e19d324f2d3029d1c304752f4d38a9360bb95/src/languages/en.ts#L94-L98).

2. **Custom bitrate:** Independent `xcloud_bitrate_mode` and `xhome_bitrate_mode` choose `auto` or `custom`; each stores a separate numeric value. Defaults are auto with stored value 20; the settings slider accepts 1–50 Mbps. The UI itself says final bitrate depends on negotiation. Sources: [display.ts L76-L99](https://github.com/Geocld/XStreaming/blob/383e19d324f2d3029d1c304752f4d38a9360bb95/src/common/settings/display.ts#L76-L99), [settingStore.ts L107-L121](https://github.com/Geocld/XStreaming/blob/383e19d324f2d3029d1c304752f4d38a9360bb95/src/store/settingStore.ts#L107-L121), [SettingDetail.tsx L240-L248](https://github.com/Geocld/XStreaming/blob/383e19d324f2d3029d1c304752f4d38a9360bb95/src/pages/SettingDetail.tsx#L240-L248), [slider L449-L485](https://github.com/Geocld/XStreaming/blob/383e19d324f2d3029d1c304752f4d38a9360bb95/src/pages/SettingDetail.tsx#L449-L485).

### Backend discrepancy: do not copy the UI and assume it works

The pinned **native React Native WebRTC** implementation's `createOffer` only optionally modifies stereo audio before setting local description; it does not consume the custom bitrate preferences. `setRemoteOffer` installs the answer unchanged. Searching the authored `src/` tree found bitrate preference references only in settings/UI, not native transport consumption. [webrtc/index.ts L230-L279](https://github.com/Geocld/XStreaming/blob/383e19d324f2d3029d1c304752f4d38a9360bb95/src/webrtc/index.ts#L230-L279).

The shipped **WebView** bundle does implement bitrate adjustment. `Stream.tsx` injects settings into the WebView. In the bundled JS, the cloud path calls `setVideoBitrate(xcloud_bitrate)` when custom mode is selected, while the other path uses `xhome_bitrate`. The offer builder invokes `_setBitrate(sdp, "video", _maxVideoBitrate * 1024)`. That helper inserts/replaces a media-level `b=AS:<value>` line. These are requested bandwidth values, not achieved throughput, and do not change the game's render rate. The packed helper is not a suitable implementation to copy blindly: its insertion loop waits for an existing `b=AS` or a subsequent `m=` section. Sources: [Stream.tsx L1950-L1954](https://github.com/Geocld/XStreaming/blob/383e19d324f2d3029d1c304752f4d38a9360bb95/src/pages/Stream.tsx#L1950-L1954), [shipped bundle line 88](https://github.com/Geocld/XStreaming/blob/383e19d324f2d3029d1c304752f4d38a9360bb95/android/app/src/main/assets/stream/assets/index-B_klBrEZ.js#L88) (search `setVideoBitrate`, `_maxVideoBitrate`, `_setBitrate`).

## Game language is a session-start setting

`preferred_game_language` is separate from application `locale`; options include `en-US`, `ja-JP`, `zh-CN`, and `zh-TW`. New session POST `/v5/sessions/{cloud|home}/play` sends it as `settings.locale`, with an empty/default preference falling back to `en-US`. Sources: [bases.ts L8-L11](https://github.com/Geocld/XStreaming/blob/383e19d324f2d3029d1c304752f4d38a9360bb95/src/common/settings/bases.ts#L8-L11), [game choices L69-L103](https://github.com/Geocld/XStreaming/blob/383e19d324f2d3029d1c304752f4d38a9360bb95/src/common/settings/bases.ts#L69-L103), [play payload L384-L414](https://github.com/Geocld/XStreaming/blob/383e19d324f2d3029d1c304752f4d38a9360bb95/src/xCloud/index.ts#L384-L414).

This preference also influences upstream catalog metadata, but differently: any `zh` preference maps catalog hydration to `zh-TW`, otherwise `en-US`, with market fixed to US. Do not conflate catalog names with actual game language. [xCloud/index.ts L984-L991](https://github.com/Geocld/XStreaming/blob/383e19d324f2d3029d1c304752f4d38a9360bb95/src/xCloud/index.ts#L984-L991).

A reused cloud session returns before the new play payload; changing a preference cannot be assumed to update an existing game's language or client profile. Fully end the session and create a new one for verification. The source proves how the preference is requested, not that every title supports or honors every locale. [session reuse L290-L320](https://github.com/Geocld/XStreaming/blob/383e19d324f2d3029d1c304752f4d38a9360bb95/src/xCloud/index.ts#L290-L320).

## What the source cannot establish

- No explicit Series S/Series X host-selection parameter appears in the inspected quality/session path. An in-game `XSS` label does not by itself identify physical cloud hardware; no source here proves a stronger host can be requested by raising bitrate.
- Upstream native FPS is incoming WebRTC `stat.framesPerSecond`, and achieved bitrate is calculated from `bytesReceived` deltas. There is no unique-image/game-engine FPS derivation in that metric. Thus a reported 60 stream FPS is not evidence of 60 distinct game frames. [webrtc/index.ts L593-L599](https://github.com/Geocld/XStreaming/blob/383e19d324f2d3029d1c304752f4d38a9360bb95/src/webrtc/index.ts#L593-L599), [bitrate L627-L637](https://github.com/Geocld/XStreaming/blob/383e19d324f2d3029d1c304752f4d38a9360bb95/src/webrtc/index.ts#L627-L637).

## Suggested XFrame scope

Expose game language for newly created sessions, keeping it separate from application/catalog language. Treat HQ client profile and custom bitrate as distinct controls. Preserve auto as the default, label HQ experimental until tested, and report measured resolution/bitrate separately from the preference. Verify Palworld language after a full session restart. Verify HQ with identical-scene throughput/resolution measurements; do not promise higher simulation/render FPS or a different host. Any future native bitrate implementation needs its own SDP correctness and live negotiation checks; the pinned native backend provides no working implementation to copy.

## HUD follow-up: measurement, opacity, and input

The native screen queries `getStreamState()` immediately and every 1,000 ms while connected. It continues collecting session-report samples when the HUD is hidden, but only publishes visible HUD state when shown. The interval is cleared on effect cleanup/disconnection. [NativeStream.tsx L2096-L2142](https://github.com/Geocld/XStreaming/blob/383e19d324f2d3029d1c304752f4d38a9360bb95/src/pages/NativeStream.tsx#L2096-L2142).

The actual video bitrate uses video `inbound-rtp` reports, with `kind == video` or `mediaType == video`. Formula: `8 * (bytesReceived - previous.bytesReceived) / (timestamp - previous.timestamp) / 1000`, displayed with one decimal as Mbps. This assumes WebRTC report timestamp milliseconds: bits per millisecond divided by 1000 equals decimal megabits per second. It does not use the configured bitrate or divide bytes by the nominal one-second timer. Zero time delta yields `--`; the first sample has an empty bitrate. [webrtc/index.ts L565-L639](https://github.com/Geocld/XStreaming/blob/383e19d324f2d3029d1c304752f4d38a9360bb95/src/webrtc/index.ts#L565-L639).

Important implementation limitations: previous report is module-global `globalThis._lastStat`, initialized to null at module load and overwritten after each video report. The inspected file has no session-close reset, no report-ID/SSRC matching, no counter-reset guard, and only checks `timeDiff !== 0`, not positive elapsed time. Multiple video reports or a new session can therefore contaminate deltas. XFrame should use session-scoped baselines keyed to the inbound report and reset on a new report, counter regression, or invalid/nonpositive timestamp delta, displaying unavailable until two valid samples exist. Sources: [initialization L20](https://github.com/Geocld/XStreaming/blob/383e19d324f2d3029d1c304752f4d38a9360bb95/src/webrtc/index.ts#L20), [delta and update L627-L684](https://github.com/Geocld/XStreaming/blob/383e19d324f2d3029d1c304752f4d38a9360bb95/src/webrtc/index.ts#L627-L684).

The video bitrate excludes audio/network overhead. Separate cumulative traffic counters prefer the largest observed succeeded candidate-pair/transport byte counter, falling back to summed inbound RTP bytes. These are distinct quantities. Its `JIT` label is actually average jitter-buffer residence time (`delta jitterBufferDelay / delta jitterBufferEmittedCount * 1000`), not RTP interarrival jitter. RTT uses a succeeded candidate pair's `currentRoundTripTime * 1000`, without selected-pair filtering. Android-specific arbitrary decode-time subtraction is also present and should not be copied into the macOS HUD. [webrtc/index.ts L642-L722](https://github.com/Geocld/XStreaming/blob/383e19d324f2d3029d1c304752f4d38a9360bb95/src/webrtc/index.ts#L642-L722).

Upstream offers shown/hidden, horizontal/vertical layout, and opacity from 0.1 to 1 in steps of 0.1. It does **not** supply simple/detailed/hidden metric presets in this native panel. `PerfPanel` shows resolution, RTT, buffer delay, FPS, frame drops, packet loss, bitrate, decode time, and battery; it applies opacity to the whole panel (`settings.performance_opacity || 0.7`) atop a black background alpha 0.5. For XFrame, increasing background transparency while preserving readable text can be a separate design choice. Sources: [display.ts L132-L160](https://github.com/Geocld/XStreaming/blob/383e19d324f2d3029d1c304752f4d38a9360bb95/src/common/settings/display.ts#L132-L160), [PerfPanel.tsx](https://github.com/Geocld/XStreaming/blob/383e19d324f2d3029d1c304752f4d38a9360bb95/src/components/PerfPanel.tsx).

In the inspected native gamepad path, holding **Menu for two seconds** opens the options modal (except portrait/Picture-in-Picture). The options include `Toggle Performance`, which flips visibility. This is a menu-access gesture, not a direct three-state HUD chord. The initial Menu down is forwarded to gameplay before the long-press fires, so copying it would risk invoking the game's menu as well. No dedicated keyboard HUD shortcut or direct HUD gamepad chord was found in the inspected native input path. A native XFrame shortcut and an edge-triggered dedicated controller combination therefore need their own design and validation, preserving ordinary game input and resetting latch state on loss of focus/disconnection. Sources: [NativeStream.tsx L948-L1036](https://github.com/Geocld/XStreaming/blob/383e19d324f2d3029d1c304752f4d38a9360bb95/src/pages/NativeStream.tsx#L948-L1036), [menu item L2598-L2603](https://github.com/Geocld/XStreaming/blob/383e19d324f2d3029d1c304752f4d38a9360bb95/src/pages/NativeStream.tsx#L2598-L2603), [toggle L2657-L2662](https://github.com/Geocld/XStreaming/blob/383e19d324f2d3029d1c304752f4d38a9360bb95/src/pages/NativeStream.tsx#L2657-L2662).

## XFrame comparison and FPS interpretation

As inspected in this working tree, `Sources/XFrame/Cloud/CloudService.swift` create() fixes settings.locale to en-US and advertises macOS desktop / 1920×1080 in X-MS-Device-Info. Catalog language=en-US is separate. `CloudVideoConnection.makeOffer()` and `CloudSignaling.exchangeSDP()` do not inject a video bitrate preference. XFrame therefore lacks both the reference HQ client profile and a custom bitrate control; the current HUD work adds measurement, not a quality override.

`LiveVideo.renderFrame()` increments decoded for every delivered native RTCVideoFrame. `MetalRenderer` increments presented on a drawable presentation of a new video frame. `XFrameApp` divides these by elapsed time. Neither examines whether adjacent images contain new game content. Existing `xframe_requirement.md` section 20 already specifies that 30 unique frames may arrive as 60 repeated transport frames and asks for three distinct metrics; unique-content estimation is still unimplemented. No controlled Palworld cadence trace was captured during this research, so actual 30 fps and its cause remain unconfirmed. Do not infer host GPU performance or physical hardware from an XSS text label or these counters alone.

Microsoft historically described xCloud as powered by custom Series X hardware ([2021 official announcement](https://blogs.windows.com/windowsexperience/2021/06/28/big-milestone-custom-xbox-series-x-hardware-now-powers-xbox-cloud-gaming-which-expands-to-windows-10-pcs-and-apple-devices/)); this is not evidence about this session's precise allocation/profile. Official [November 2025 resolution announcement](https://news.xbox.com/en-us/2025/11/25/xbox-november-update-gaming-copilot-full-screen-experience/) limits enhanced quality to selected titles and up to 1440p for Ultimate subscribers. Neither source guarantees a higher game render rate from a bitrate preference.
